Java笔记44-SpringMVC请求处理

Spring MVC 解决的是表现层问题。它关注的不是“业务怎么做”，而是 HTTP 请求怎么进来、参数怎么绑定、结果怎么返回给页面或前端。

所以 Spring MVC 的入口不是某个 Controller，而是 DispatcherServlet。

Spring MVC 请求处理链

DispatcherServlet 被称为前端控制器，并不是因为它自己完成所有事情，而是因为它站在请求入口位置，负责调度 Spring MVC 内部的一组组件。一次请求进入之后，大致会经过下面这条链：

HandlerMapping 建立路径与处理方法之间的映射；HandlerAdapter 配合参数解析器完成绑定并调用方法；响应阶段再由视图解析器或消息转换器处理返回值。

所以 Spring MVC 并不是简单把 Servlet 包了一层，而是把请求处理拆成了可扩展的多个环节。拦截器、参数绑定、数据校验、异常处理、JSON 转换，从机制上看都是在这条处理链上增加能力。

@ResponseBody 与消息转换

@ResponseBody 改变返回值的处理方式：

当 @ResponseBody 打开之后，返回值就不再交给 JSP，而是直接写入响应体。配合 mvc:annotation-driven，对象通常会被转换成 JSON。

是否返回页面或响应体属于接口契约的一部分，不能仅按项目是否前后端分离判断。

与之经常一起出现的是 @RequestBody。@ResponseBody 关注的是“响应怎么写出去”，@RequestBody 关注的是“请求体怎么读进来”。表单提交时，参数通常来自 query string 或 form data；前端提交 JSON 时，请求数据通常在 body 中，这时就需要消息转换器把 JSON 反序列化成 Java 对象。二者方向不同，但都依赖 Spring MVC 的消息转换机制。

相比手动判空，这种写法更接近“声明式参数处理”。

这里还有一个容易被忽略的细节：可选参数更适合使用 Integer、Long 这类包装类型，而不是 int、long 这样的基本类型。因为请求参数不存在时，包装类型可以接收 null，基本类型却无法表达“没有值”这个状态。如果方法参数又没有设置默认值，就很容易出现绑定失败。分页参数之所以常配合 defaultValue，正是为了让请求缺省时仍然有稳定的业务含义。

请求处理链

把这一套代码串起来，请求的大致流向其实很清楚：

如果是页面返回：

  • Controller 处理参数
  • 把数据放进 Model 或 ModelAndView
  • 视图解析器找到 JSP

如果是接口返回：

  • Controller 处理参数
  • 返回对象或数据
  • 消息转换器序列化成 JSON

请求处理边界

环节 负责什么
DispatcherServlet 统一接收请求
HandlerMapping 找到匹配的控制器方法
Controller 处理请求参数和业务入口
Model / ModelAndView 准备返回数据
视图解析器 定位页面
消息转换器 把对象转成响应内容

页面返回和 JSON 返回的判断应由接口契约决定。String 返回值在没有 @ResponseBody 时通常是视图名，加入消息转换后才会被序列化为响应数据；参数绑定还应结合校验和异常处理，不能只依赖 Integer.parseInt 等转换调用。
